# 7-Zip 与当前方案的同文本实测

本文是 AI 生成的工程实验记录，不是学生本人撰写的提交报告。

## 条件

- 原文：austen.txt，2,664,245 字节。
- 原文 MD5：`967205af325fc85e5783b6847eaf8dba`。
- 7-Zip 版本：`7-Zip (z) 25.01 (x64) : Copyright (c) 1999-2025 Igor Pavlov : 2025-08-03`。
- Python：`3.12.14 (main, Aug 25 2026, 14:00:49) [Clang 22.1.3 ]`。
- 系统：`Linux-6.18.55-x86_64-with-glibc2.41`。
- 7-Zip 使用单线程 `-mmt=1`，关闭文件时间戳；PPMd 内存参数为 64 MiB。
- 每个 7-Zip 候选都实际解压并逐字节比较，全部通过；当前方案也重新编码并核对与已有 compressed 完全一致，然后在隔离目录独立解码验证。
- CPU 时间通过 Linux resource 的子进程/当前进程用户 CPU 时间增量测量。表中时间为单次实测，运行环境变化会影响结果。

7-Zip 文件大小包含 7z 容器头和文件名等开销，但没有计入 7-Zip 原生解码程序。
当前方案的解码器字节码为 7,402 字节，按课程规则计算的总大小为 **622,787 字节**。

本次候选中最小的是 **PPMd-order-7-64MiB：590,953 字节**，相对当前压缩数据小 **3.97%**。
这是已测试参数中的最小值，不是 7-Zip 所有可能参数的全局最优结果。LZMA2 本次两个设置均大于当前方案。

PPMd 的原生实现解码明显更快；这是不同语言和实现的实测，不能归因于算法本身必然获得相同比例的加速，也不能视为纯 Python PPMd 解码时间。

## 对课程提交的含义

7-Zip 是工具，可选择多种算法。此次 PPMd 的结果说明更成熟的 PPM 建模有改善本文件压缩率的实际空间。

课程允许使用外部工具编码，所以可以用 7-Zip 产生编码数据；但最终 decompress.py 只能导入 struct/decimal，不能调用 7-Zip 或导入 pyppmd、py7zr、lzma 来解码。现有 decompress.py 也不能解码 7z/PPMd 文件，它使用的是本项目自定义 APM1 格式。

如果保留整个 590,953 字节的 7z 文件，需要另外实现符合课程要求的纯 Python 7z/PPMd 解码器。要优于目前 622,787 字节的总大小，新解码器 .pyc 必须 **小于 31,834 字节**，且在 ECE 环境下用户 CPU 时间小于 1,200 秒、输出逐字节一致。若改用原始 PPMd 流而不保留 7z 容器，需重新统计码流与解码器的总大小。

目前没有实现或验证这一纯 Python PPMd 解码器，因此 native 7-Zip 的优势不等于已经得到更小的合规提交版本。正式提交的 compressed 与 decompress.py 未因本实验更改。

## 复现

安装或准备一个可信来源的 7zz/7z 程序，然后运行：

```bash
python tools/benchmark_7zip.py --sevenzip /path/to/7zz
```

实测结果写入 docs/sevenzip_results.json。7-Zip 测试归档和隔离解码输出仅放在临时目录。

典型 PPMd 参数：`-mx=9 -m0=PPMd:mem=64m:o=7 -mmt=1`。完整参数和实际识别的压缩方法保存在 JSON 中。

7-Zip 官方格式说明列出了 LZMA、LZMA2 和 PPMd 等方法：[7z Format](https://www.7-zip.org/7z.html)。
